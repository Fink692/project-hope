# Project Hope 1.1.0 — A friendlier front door

Project Hope 1.1 makes the platform easier to adopt for the people it is built to serve: charity teams who need useful technology, not another technical project.

## What changed

- One guided setup command for Windows, macOS, and Linux.
- A Windows double-click launcher for coordinators who do not want to learn terminal commands.
- Friendly `setup`, `start`, `stop`, `status`, `logs`, and `doctor` commands that explain what to do next.
- A plain-language [Getting Started for Charities guide](https://github.com/Fink692/project-hope/blob/main/docs/GETTING_STARTED_FOR_CHARITIES.md) with setup, daily use, and troubleshooting instructions.
- A first-run in-app guide that shows new teams the first three steps without infrastructure jargon.
- CI coverage for both setup helpers, plus updated 1.1.0 release metadata across web, mobile, API, and OpenAPI surfaces.

## The experience

Install Docker Desktop or Podman Desktop, open it, and run one guided command. Project Hope starts the services, waits for the health check, opens the workspace, and shows the local sign-in details. The helper never deletes named data volumes when stopping the workspace.

## Quality signals

- Backend, web, mobile, Compose, production configuration, and onboarding quality gates passing in GitHub Actions.
- Guided Windows setup smoke verified against a rebuilt local stack: health 200, web root 200.
- Expo Doctor: 20/20 checks passing.
- No credential-shaped values found in the published source tree.

## Still required before real data

Production still needs organization-owned domain/TLS, strong secrets, MFA-backed identity, email, encrypted backups, restore testing, staging, and native app signing. The [production deployment guide](https://github.com/Fink692/project-hope/blob/main/docs/operations/production-deployment.md) remains the source of truth for those controls.

Project Hope should feel like a helping hand—not a new IT department.
